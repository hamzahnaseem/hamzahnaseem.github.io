Catalog search that tolerates partial failure

Two services share one vector index. An indexer fed by Kafka embeds catalog items and reports success or failure for every item. A search service answers queries with filters and a two-stage re-ranker. I designed and implemented both at Vroozi, in a team of four engineers. The purchasing application and the agent from case study 1 call the search.

Context and constraints

Vroozi is a procure-to-pay platform covering purchasing, approvals, supplier collaboration and accounts payable. Its purchasing application lets a buyer search catalog items; the agent in case study 1 searches the same index. A buyer sees only items in their own unit and catalogs. The search service has run since late 2023 and the Kafka indexer since late 2024; both are in production today.

Three constraints shaped the design. Item changes must land without re-indexing a whole catalog. A batch can fail in part, and the producer must learn which items to resend. A query may have no good match, and the search should say so.

My role

I designed and implemented the catalog search stack: the Kafka indexer, the search service and the re-ranker, plus the purchasing-app side. We built it as a team of four engineers, pairing on the hard parts and reviewing each other’s pull requests.

In the purchasing application and the index, I built:

  • The similarity-search and Smart Chat UI against the search service, with user feedback and empty-result handling.
  • The AI smart-search entry point on the shopper catalog search bar: product search, add to cart, session restore and purchase-request creation. It re-keys product cards when my join node from case study 1 replaces them.
  • Automatic category-code assignment for extracted line items, through the category search.
  • Index fields for part number, unit of measure and manufacturer part ID, for the heuristic to score.

Architecture

The diagram shows two paths over one index. Above, indexing: stream, consumers, three embedding providers (two dashed as external), two stores (one active), result message. Below, querying: caller, search service, cache, filtered vector search, heuristic boosts, LLM stage.

Read this diagram as steps
  1. A platform service publishes catalog changes in batches, each item with its id and text.
  2. Separate consumers embed items, delete items and vectorize categories.
  3. Items are embedded with sentence-transformers (all-mpnet-base-v2), categories with Google GenAI, in one retried call per batch.
  4. Items are bulk-upserted into Elasticsearch; only the items the store rejects are retried, within a bound.
  5. A result message lists the succeeded and failed ids.
  6. On a query, the search service embeds the buyer's description, through a cache.
  7. A vector search filtered to the buyer's unit and catalogs returns the top 25 candidates.
  8. Heuristic boosts run; then an LLM stage picks one candidate or declines all.
  9. The ranked results return to the purchasing application or the agent's catalog search tool.

A bulk endpoint runs up to 50 searches in parallel. A material-group mapping search assigns category codes to extracted line items.

How this was evaluated

The evaluated component is the re-ranker. A black-box harness sends each document line through the search end to end and scores the reply. The team labeled each line with the expected item or no match. The metrics are first-pick accuracy, recall at K and correct no-match declines. Three setups are compared: no re-rank, heuristic only, and heuristic plus LLM. Adding the LLM stage took correct declines from 19 to 28 of 28 no-match lines. First-pick accuracy across the set went from about 78 percent to about 95 percent.

Decisions

1. A separate Kafka-fed indexer, rather than embedding inside the search service

Chosen. A separate service consumes the Kafka streams, embeds, upserts into Elasticsearch and publishes per-item results; the search service only reads. In both, the provider (sentence-transformers, OpenAI, Google GenAI) and store (Elasticsearch, MongoDB) are set by configuration. Catalog items run on sentence-transformers with Elasticsearch in production.

Considered. The older path, still in the code: a pipeline in the search service that re-indexes a whole catalog, with no per-item result.

Cost. Two services must agree on the embedding model, by configuration. Partial success covers the index write only; a failed embedding call fails the whole batch. Failed items are reported for the producer to resend, not requeued.

2. A heuristic-plus-LLM re-ranker, rather than vector similarity alone

Chosen. Vector similarity fetches the top 25 candidates; two stages follow, each switched on per request. The heuristic’s strongest boost is a unit price within 10 percent of the buyer’s price. It also boosts an exact part number, falling back to manufacturer part ID, and an exact unit of measure. Boosts only add, so description similarity stays dominant. The LLM stage sends the candidates through the LLM service to Gemini 3.1 Flash-Lite, which picks one or declines all. Its self-reported confidence never enters the published score.

Considered. Vector similarity alone: a score orders candidates but cannot say whether the top one is right, or whether any is. Heuristic boosts alone were the middle setup.

Cost. Each LLM call adds a bounded wait, and bulk searches multiply the calls. The search depends on the LLM service at query time; if that call fails, results keep the heuristic order.

Failure modes and controls

  • Items rejected by the store. Each outcome is reported; only failed items are retried, within a bound. Every item lands in the result message once.
  • Embedding provider failures. The call is retried with exponential backoff, within a bound.
  • Redelivered or duplicate messages. Writes are upserts keyed by item id; deleting an absent item counts as success.
  • Re-ranker errors. A stage that raises an error leaves the order from before it.
  • Wrong re-ranker configuration. It is validated at startup, and the service fails fast.
  • Cross-tenant results. The buyer’s unit and catalog scope is applied server-side on every query.

Results

Every item comes back to the producer as succeeded or failed, so a partly failed batch is resent item by item. A buyer gets a ranked list scoped to their unit and catalogs, or a decline when nothing matches.

What I would change

I would make index-time and query-time embedding share one model setting and one text-building function, so they cannot drift. I would also make the LLM stage fail open, so a missing or malformed model reply falls back to the heuristic order.
