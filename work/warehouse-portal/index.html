Context and constraints

Panavid’s public product is Panavid Live, a webcasting platform I also worked on as a full-stack developer. The warehouse portal is a separate, internal tool for Panavid’s warehouse workers. They use it to track every item that goes out for rent or sale.

A worker scans an item’s barcode in the portal. Scan validation checks the scan against inventory before accepting it. The item must exist, and its state must allow the current flow, such as available to check out. Before the cache, every scan waited on a server lookup, and workers paused after each scan for confirmation.

Three constraints shaped the design. A worker needs a scan’s answer before moving to the next item. The devices work over warehouse Wi-Fi, so every server round trip adds a wait to every scan. With 100+ workers changing the same inventory, each device’s view has to follow everyone else’s changes.

My role

We were a team of 14 at Rolustech. I implemented major features, coordinated requirements with the team and broke the work into tasks. I made design decisions on the front end and the Node.js server, and ran the impact analysis behind them. These parts were mine.

  • Global scanning across the portal, with a priority queue that orders scans for its various user flows.
  • The inventory cache on the device. I integrated Dexie, a library over IndexedDB, to hold the warehouse inventory on each device, and moved scan validation onto that copy.
  • Real-time inventory sync. Inventory state reaches every device over an MQTT publish-subscribe model, and each device patches its copy.
  • Flow diagrams and architectural decisions for the portal, which I worked out with the team.
  • Load time. I split the Angular front end into modules that load on demand, which cut its load time.

Architecture

The diagram shows one scan and one inventory change. On a worker’s device: the portal, global scanning, the priority queue, the user flows and a cache labelled “IndexedDB via Dexie”. Off the device: the Node.js server, an MQTT broker on AWS IoT Core, and other workers’ devices subscribed to it.

Read this diagram as steps
  1. Up front, the device loads the warehouse inventory from the Node.js server into IndexedDB through Dexie.
  2. A worker scans an item's barcode; global scanning picks up the scan.
  3. The scan enters the priority queue, which orders scan work across the portal's user flows.
  4. The flow validates the scan against the local copy, with no network call.
  5. The worker sees the result at once and scans the next item.
  6. The flow submits its work to the Node.js server. The server re-checks each scan against its own data and rejects it if the item has changed.
  7. The server updates inventory state and publishes the change over MQTT to AWS IoT Core.
  8. AWS IoT Core delivers the change to every subscribed device.
  9. Each device patches its cached copy of the item, so its next local check sees the change.
  10. Alongside these updates, each device refreshes its cached inventory after a set interval.

Decisions

1. Validate scans against an inventory cache on the device

Chosen. Each device stores the warehouse inventory in IndexedDB through Dexie. Scans are checked against that copy with no network call. MQTT updates and a refresh after a set interval keep it current.

Considered. Querying the server on every scan, which is how scans worked before the cache. It is simpler and always fresh. But every scan pays a network round trip on warehouse Wi-Fi, and workers paused after each scan.

Cost. The cache can be stale when another worker changes an item; the MQTT sync and the timed refresh narrow that gap. Every device has to load and store the inventory up front. The portal owns cache invalidation and the IndexedDB schema versioning. The server still re-checks each scan against its own data on submit. A scan accepted on the device is rejected there if the item has changed.

2. Push inventory changes over MQTT instead of polling or WebSockets

Chosen. The Node.js server publishes each inventory change to an MQTT broker, AWS IoT Core. Every device subscribes and patches its cache. MQTT’s topic-based fan-out lets one published change reach every subscribed device.

Considered. Polling the server, which is simple. But 100+ workers polling means constant load, and a change can lag by up to the polling interval. WebSockets or Socket.IO, which can push updates. But they leave the fan-out to every device to be built by hand.

Cost. A broker to set up and secure, here AWS IoT Core. Duplicate messages could arrive and had to be ignored.

Failure modes and controls

Each line gives a failure class and what the portal did about it.

  • Stale cache: another worker changed the item after this device loaded it. Each device patches its copy from MQTT updates and refreshes its cached inventory after a set interval. The server re-check on submit catches anything still stale.
  • Duplicate scans: scanners often read the same barcode twice in quick succession. The repeated read is ignored, so the scan counts once.
  • Duplicate MQTT messages: the same update can reach a device more than once. The device ignores the duplicate.
  • Offline device: a device can drop off the warehouse Wi-Fi. Scanning is blocked while the device is offline.
  • Two workers scanning the same item: each device can accept the scan against its own copy. The server accepts the first submit and rejects the second.

Results

The portal was in production when I left, used by 100+ warehouse workers. Workers get a scan's result at once and can scan continuously, with no pause for a server confirmation. The server stays out of the per-scan check. It re-checks and records submitted work, and keeps every device's copy current. Inventory state stays consistent across devices, because each change the server records is published to all of them over MQTT.

What I would change

I'd add a service worker to cache the app shell, so repeat loads don't wait on the network.
