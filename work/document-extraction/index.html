Changing models without a deploy

A pipeline that turns invoices, memos and purchase-request documents into structured data, with Gemini on Vertex AI as the production default. Each document type's model comes from layered configuration and changes by reload or per-request override, with no code deploy. I designed and implemented it at Vroozi, in a team of four engineers.

Context and constraints

Vroozi is a procure-to-pay platform connecting purchasing, approvals, supplier collaboration and accounts payable. Its purchasing application takes in invoices, memos and purchase-request documents. The pipeline’s purchase-request side ships as SmartPR, announced in Vroozi’s Feb 2026 launch post. Documents arrive as PDFs, including multi-page scans.

Four constraints shaped the design. Model lines are retired and replaced, so a document type’s model must change without a code deploy. Each model family supports different features and parameters. Data-residency rules limit where a document may be sent. The model answers in text, and a long document can come back with rows missing.

My role

I designed and implemented the document-extraction pipeline that turns invoices, memos and purchase-request documents into structured data, along with its purchasing-app side. We were a team of four engineers, and we paired on the hard parts and reviewed each other’s pull requests.

In the purchasing app, I:

  • extended the line-item bulk-upload dialog for Smart Document Request
  • added PDF upload as a source of purchase-request line items
  • moved the PDF-to-purchase-request flow into a background job
  • extended it to more file types and to draft purchase requests from email-intake attachments
  • added automatic category codes for extracted lines
  • built the unified notifications and background-jobs feature these flows report through
  • integrated the smart-coding model endpoints for invoices and fixed OCR-prediction highlighting

Architecture

The diagram shows one document’s path. Its nodes: the application, the extraction endpoint, the configuration merge, the page images or text, the model factory, the provider with its fallback, the recovery parser, the Pydantic model, validation and repair. The drawing stacks the merge layers in the code’s order, and the model factory applies the capability gate.

Read this diagram as steps
  1. The application posts a document and its document type to the extraction endpoint, with an optional configuration override.
  2. Configuration resolves in three layers: application defaults, then the request, then the per-document-type override. The merge is set-aware: an omitted field inherits, while an explicit null or false still applies. It skips Pydantic's validators, so conflicting settings, such as a thinking budget against a reasoning effort, are resolved explicitly.
  3. The PDF or its page images go to a vision model, or a text-extraction step runs first. Multi-page scans go as one image per page, so the provider's PDF compression cannot drop line items.
  4. The model factory builds the model with only the features its family supports.
  5. The call goes to a US endpoint first, then once to Vertex global if it fails after the provider's own retries.
  6. The prompt carries the output schema; the model answers in text with a JSON block.
  7. The recovery parser handles fenced, truncated and duplicate-key JSON, rejects schema look-alikes and validates against the Pydantic model.
  8. Validation reconciles totals, tax, discounts and per-line prices against the document.
  9. Values are normalized and the structured record returns to the application.

The layering let document classification run on Gemini 3.1 Flash-Lite, a small model, instead of the extraction model. On every classification test document it matched the extraction model’s accuracy, for about a fifth of the cost.

How this was evaluated

The pipeline is checked against about 230 labeled documents under version control, each PDF with a JSON file of expected values. A 41-document purchase-request regression set is run when a model or a prompt changes, and its report is cited in the change. A LangSmith-based runner scores each document with a weighted composite of three sub-scores. The header sub-score compares each field. The line-item sub-score pairs extracted rows with expected ones and penalizes missing and extra rows. The totals sub-score allows a tolerance. A run passes when the average meets a fixed threshold. The runs call real model APIs, so they are launched by hand. The team wrote the labels and checked them by hand against the PDF, field by field.

Decisions

1. Put the schema in the prompt and recover the JSON, not forced tool-calling

Chosen. The document type’s Pydantic schema is appended to the prompt as format instructions, and the model answers in text. A recovery parser tries fenced blocks, then the text after a fence, then the text from the first brace.

Considered. We evaluated extraction across Gemini, Claude and GPT models through one model factory. A schema in the prompt with our own parser behaved the same on all of them. Forced tool-calling and structured-output support differed by provider; some models needed workarounds just to call a tool reliably.

Cost. This kept a model swap a configuration change, at the price of owning the parsing. The schema echo under Failure modes came from that. A failed parse costs a whole model call. Whether a model echoes its schema is now one of the checks when a newer model is tried.

2. A primary route plus one fallback hop, not a global primary

Chosen. The factory builds each model for a US endpoint on Vertex AI and wraps the same model on Vertex global behind it. The fallback fires once, after the provider client’s own retries fail. Models already on global or in Model Garden get no fallback. Any model can override or disable its fallback where residency is stricter.

Considered. Vertex global as the primary route, which would send every document to global, not only the failed calls.

Cost. Retries stack: provider retries, then the fallback, then the outer retry loop.

Failure modes and controls

  • Schema echo. A newer Gemini model started repeating the schema before its answer. The parser took the schema as the result, which validated as an empty extraction with no error. I changed the parser to reject anything it recognizes as a schema and recover the real answer behind it. I proved the fix by replaying every affected document; each re-parsed in full.
  • Malformed or cut-off output. Output that fails the recovery parser or the Pydantic parse is retried with varied sampling settings, a fixed number of times.
  • Truncated invoice line items. Validation flags as blocking any invoice whose line items fall short of the subtotal, the signature of a truncated extraction. An opt-in repair loop re-prompts the model with the violations, bounded in turns and time, and keeps the best result. It is off by default. Measured against runs without it, repair cost 21 to 134 percent more tokens for an accuracy gain of 0.01 to 0.02.
  • Collapsed purchase-request lines. A detector compares the extracted rows with the document text and retries when grouped lines have merged into one.
  • Unsupported parameters. The factory drops a thinking budget or a reasoning-effort level the model does not accept and maps effort onto the provider’s own parameter.
  • Provider failure and stacked retries. A failed call takes its one fallback hop. Provider retries, the fallback and the outer loop each add attempts, so a document that fails everywhere costs several calls.

Routing playground

How a request is routed in the configuration-driven pattern this pipeline uses: three layers of settings are merged in the pipeline's order (app defaults, then the request, then the document type's settings, which have the last word), the resolved model's card gates the parameters, a fallback chain reroutes around an outage, and a response cut short at the output cap is retried once with the cap doubled. The example runs on invented providers, models and regions; every step names the layer or rule that produced it.

Results

A purchase request or an invoice comes back to the application as a validated record: header fields, line items and totals. A model or a parameter changes for one document type through configuration. A per-request override lets one tenant try a newer model before the default moves, with no deploy. Each change can be scored against the labeled set and the regression set.

What I would change

I would try the model's structured-output mode instead of putting the schema in the prompt. That removes the schema-echo class rather than parsing around it. I would also add a semantic retry for an extraction that comes back empty.
