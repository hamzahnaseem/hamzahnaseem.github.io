A purchasing agent that pauses so the browser can act

A multi-turn LangGraph agent: buyers search a catalog, manage a cart and create purchase requests in chat. It pauses before cart and purchase-request actions so the browser can run them, then resumes with the result. Built by four engineers at Vroozi; my part spans the chat client, the graph and its evaluation suite.

Context and constraints

Vroozi is a procure-to-pay platform; its in-app assistant, Smart Chat, was announced publicly as “Vroozi AI” on 16 November 2023.

Smart Chat lets a buyer find catalog items, build a cart and raise a purchase request in conversation. The buyer sees cards as they are found and asks for items to go into the cart or a purchase request. For tenants that also buy from an external marketplace such as Amazon Business, one conversation searches both sources.

Three constraints shaped the design. The cart and purchase-request services live in the browser with the user’s session, so the graph cannot change them itself. Sensitive data must not reach the model in the clear. A reply has a latency budget, so every extra model call has to earn its place.

My role

We were four engineers, and none of us had built an agent before. We designed together, paired on the hard parts and reviewed each other’s pull requests. These parts were mine.

  • The chat client: the stream reader for text and attachments (product cards and action instructions), the relay proxy, the stream’s access token and UI fixes. I built the feedback loop from a chat rating to the reply’s trace in LangSmith. I built a new entry point from the catalog search bar, with its own landing view.
  • The streaming handshake for client actions (Decisions): I built the client end and worked on the server end.
  • The marketplace result handling: the join node (Decisions), a source marker on the add-to-cart tool, and a newer vendor payload version behind a per-environment switch.
  • The transcript rebuild from the checkpoint. It never re-runs a client action, so a restored thread cannot repeat a spend action. It checks session ownership and restores masked values against a request-local copy of the mapping.
  • I also worked on the evaluation suite, the completion grader and the per-session reversible mapping behind the mask-and-restore boundary.

We designed the graph, the retrieval subgraph and the checkpointer as a team; I extended the graph with the nodes above.

Architecture

The diagram shows the graph behind one conversation turn. Catalog search runs in the tool node, apart from the retrieval subgraph. Tenants with the marketplace run a second variant with two more search tools and my join node.

Read this diagram as steps
  1. The browser sends the buyer's message to the streaming endpoint.
  2. The endpoint starts a run of the graph on that conversation's thread.
  3. The agent node trims the history and calls the model provider. What crosses the mask-and-restore boundary is masked going out and restored coming back.
  4. The router reads the reply: a tool call, or a final answer.
  5. Catalog search runs as a tool in the tool node; a document question goes to the retrieval subgraph and its own index.
  6. Graders check the documents, the answer's relevance and its grounding; a failure rewrites the query or regenerates the answer.
  7. Results return to the agent node, which calls the model again; cards and text stream to the browser.
  8. For a cart or purchase-request call, the graph stops before the client-action node and the checkpointer saves the state.
  9. The browser runs the action and posts the result to the same endpoint; the graph resumes from the checkpoint.
  10. The final answer streams to the browser and the stream ends.

How this was evaluated

The agent is checked against fixtures. A fixture holds a prompt with the expected tool call, an expected answer with references, or a scripted conversation with mocked tool results. We wrote and checked the expected outputs by hand. A LangSmith-based runner scores each fixture with three evaluators. Tool-call match compares the chosen tool and its arguments; embedding similarity and an LLM judge compare the answer with the expected text. A run passes when the average of the chosen metric meets a fixed threshold. The runs call real model APIs, so they are launched by hand and cited when a model or prompt changes. I worked on the fixture conversations and the three evaluators.

Decisions

1. Pause the graph and let the browser run cart and purchase-request actions

Chosen. The cart and purchase-request tools have empty bodies, and the graph is compiled with interrupt_before on them. When the model calls one, the turn ends and the stream tells the browser which call to run. The browser posts the result to the same endpoint, and the agent continues from a tool message carrying the original call id.

Considered. Running these tools on the server, as catalog search does; the browser already held the session, the cart state and the services that change them. For the marketplace, a sync that mirrored each cart change to the vendor as it happened. We replaced it with one sync at purchase-request creation, because a browser-side cart write never reports back within the same turn.

Cost. Every cart action takes two requests, and the model cannot act on a confirmed write in the same reply. The saved state lives in memory, so a session is pinned to the process and graph variant that hold it. The pause is a hand-off, not a confirmation step: the browser acts at once.

2. One card budget per reply, applied by a join node

Chosen. In the marketplace variant a join node runs after every tool round. It pools every search in the reply, gives the catalog two slots and the marketplace three, and passes unused slots across. Marketplace items come first, and every item is numbered. It rewrites the tool results so the model sees only what the buyer sees, with honest counts of items found but withheld.

Considered. Letting each search tool emit its own cards, the old behavior. The buyer saw more cards than the model listed, so “add the last item” added the wrong product. A keyword-overlap filter, built, measured and reverted after it silently dropped a notebook result for a laptop query. An LLM relevance judge, rejected because it adds a model call to every search inside the latency budget.

Cost. The node adds steps to every tool cycle, so the marketplace variant needs a larger step limit. The stream handler needed a replace path, and it must flush held-back cards on every exit or the transcript records cards the buyer never saw. Marketplace first could steer spending away from preferred catalog suppliers; the two reserved catalog slots are the protection.

Failure modes and controls

  • Runaway loops. A step limit per turn; when it trips, the buyer is told the turn ran long and sees the cards found so far. I wrote that handling.
  • Context growth. The history is trimmed to a character budget before each model call, keeping the system message.
  • Irrelevant retrieval and off-target answers. Graders check each retrieved document and the answer’s relevance; a failure rewrites the query and retrieves again, within a bound.
  • Unsupported answers. A groundedness grader checks the answer against its documents, and a failure regenerates it. That loop is bounded by the graph’s step limit, not by a per-loop retry cap.
  • Personal data reaching the model. It is masked before entering the graph and restored before reaching the browser, with a mapping kept per session.
  • Truncated replies. A completion grader flags a reply that was cut off, and the agent re-prompts itself with a correction, up to a fixed number of attempts.
  • Lost client actions. The paused state is checkpointed before the stream ends, and the posted result is matched to the pending call by id.

Results

For a buyer, the assistant puts search, cart and purchase request into one conversation. Cards arrive as each search finishes; items go into the cart and a purchase request follows, without leaving the chat. Questions answered from indexed documents come back with references, or with a plain no-answer. A conversation can be restored from the checkpoint without re-running any action.

What I would change

I would move the checkpointer from per-process in-memory SQLite to a shared store. A paused cart or purchase-request action would then survive a restart or a different worker. I would also close the loop on client actions, so the server always learns the outcome, failures included. As of October 2026, LangGraph's documentation recommends the interrupt() function over static breakpoints for human-in-the-loop work in new code.
