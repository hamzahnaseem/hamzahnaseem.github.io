Bulk indexing when some items fail

How a Kafka-fed indexer reports success or failure for every catalog item, so a partly failed batch is resent item by item instead of all over again.

27 Oct 2026

Catalog search at Vroozi runs on a vector index: every catalog item is embedded and stored in Elasticsearch, and buyers and the purchasing agent search it. Catalogs change all the time. Prices move, items are added and retired, whole catalogs are replaced. I designed and implemented the indexer that keeps up with those changes: it reads batches of changed items from Kafka, embeds them, writes them to the index and reports back.

The older path re-indexed a whole catalog at once and reported nothing per item. If anything went wrong, all you knew was that something, somewhere, had not made it. The new indexer had one requirement that shaped everything else: a batch can fail in part, and whoever sent it must learn exactly which items to send again.

A bulk request is many results, not one

Elasticsearch’s bulk API takes many operations in one request, and every operation gets its own result. The request as a whole can succeed while some of the items in it fail: a document that does not fit the mapping, a version conflict, a write rejected while the cluster is busy. If you only look at whether the request succeeded, those items disappear quietly.

The Python client’s bulk helpers raise an error by default as soon as an item fails, which loses the per-item picture the other way. Turned off, streaming_bulk hands back one result per operation, and the indexer sorts every item into one of two lists:

One result per item 
from elasticsearch import helpers


def write_batch(es, index, docs):
    actions = (
        {
            "_op_type": "update",
            "_index": index,
            "_id": doc["id"],
            "doc": doc,
            "doc_as_upsert": True,
        }
        for doc in docs
    )
    succeeded, failed = [], []
    for ok, item in helpers.streaming_bulk(
        es, actions, raise_on_error=False, raise_on_exception=False
    ):
        (succeeded if ok else failed).append(item["update"]["_id"])
    return succeeded, failed

A simplified sketch, not the production code, but the shape is the same: no exception decides what happened to an item; its own result does.

Retry only what failed, and embed only once

Embedding is the expensive step, and the write is the step that fails now and then. So the indexer embeds the whole batch once, before the first write, and its retries repeat only the write. After each attempt it keeps the items that succeeded and sends again only the ones that failed, within a bound, with a pause between attempts.

One detail matters more than it looks. Successes accumulate across attempts, but the failed list is replaced after each attempt, not added to. An item that failed the first time and went through the second must leave the failed list, or the producer will resend something that is already indexed. At the end, every item in the batch is in exactly one of the two lists, exactly once.

Retrying the write 
async def index_batch(docs, attempts, pause):
    embed_all(docs)  # once, before any write
    succeeded, pending = set(), docs
    failed = []
    for _ in range(attempts):
        ok, failed = write_batch(es, index, pending)
        succeeded.update(ok)
        if not failed:
            break
        failed_ids = set(failed)
        pending = [doc for doc in pending if doc["id"] in failed_ids]
        await asyncio.sleep(pause)
    return sorted(succeeded), failed

Tell the producer, item by item

When the batch is done, the indexer publishes a result message on a Kafka topic of its own: the batch id, the ids that succeeded and the ids that failed. The purchasing side reads it and resends the failed items.

The indexer does not requeue failed items itself. The producer owns the catalog, so it is the one that knows whether an item still needs indexing. By the time a retry would run, the item may have changed again or been deleted, and an indexer resending its own copy could write an old version over a newer one. Reporting, and letting the owner decide, keeps the indexer from writing stale data.

Where partial success stops

Partial success covers the index write. It does not cover embedding. The embedding call is made for the whole batch, and if the provider fails, there is nothing to write for any item. That call is retried with exponential backoff, within a bound. If it still fails, every item in the batch is reported as failed. It is the honest answer: the indexer does not know of any item that made it, so it does not claim one.

That is a real cost. One bad moment at the embedding provider sends a whole batch back, not a few items. Embedding item by item would narrow it, at the price of many more calls and a slower indexer for the normal case, where nothing fails.

There is a quieter cost in having a separate indexer at all. The search service embeds queries, the indexer embeds items, and both must use the same model or search results silently degrade. Today they agree through configuration. If I did it again, I would make index time and query time share one model setting and one function that builds the text to embed, so the two cannot drift.

What I would keep

  • Treat a bulk call as many small results. Never let one exception, or one success code, stand for all of them.
  • Make every item end up in exactly one outcome, exactly once, and test the case where an item fails and then succeeds.
  • Separate the expensive step from the flaky step, so that a retry repeats only what failed.
  • Let whoever owns the data decide what to resend. The indexer reports; it does not guess.
