A join node for parallel tool calls in LangGraph

Two parallel searches each sent their own cards, so the buyer saw eight items while the model listed three. A join node gave every reply one budget.

27 Oct 2026

Smart Chat, the purchasing assistant in Vroozi’s procure-to-pay platform, searches the company’s own catalog. Some tenants also buy from an external marketplace such as Amazon Business, and for them one question searches both. The model calls the catalog search and the marketplace search in parallel, and the buyer gets product cards from both in the same reply.

That is where the bug lived. Each search tool sent its own cards to the browser the moment it finished. The model, writing the reply, picked a few items from what it had read and listed those. In one conversation the buyer saw eight cards while the model’s reply listed three. When the buyer said “add the last one”, the model added the last item of its list, and the buyer meant the last card on the screen. Wrong product in the cart.

The screen and the model’s view of the conversation had come apart. This article is about the node I added to put them back together.

What did not work

We tried the cheaper fixes first.

  • A relevance filter on keywords. We built it, measured it and reverted it. A “Notebook” result for a “laptop” query shares no words with the query and was silently dropped.
  • An LLM relevance judge. Rejected: it adds a model call to every search, inside a reply that already has a latency budget, at a cost that never goes away.
  • Prompt edits. We tried several. One scored perfectly on our test set, and we reverted it anyway. A prompt makes the right behaviour more likely; it cannot make it certain, and “the cart holds what the buyer pointed at” has to be certain.

The fix had to be structural. Something had to decide, in one place, exactly which items the buyer sees, and then show the model exactly those.

One node where the results meet

In LangGraph, a tool node runs the model’s tool calls, in parallel when the model asks for several. Neither search knows what the other returned. The first point in the graph where both results exist is the step after the tool node. So I added a node there, between the tools and the model. Simplified, the wiring looks like this:

Wiring the join node 
builder.add_node("agent", call_model)
builder.add_node("tools", ToolNode(tools))
builder.add_node("join", join_search_results)

builder.add_conditional_edges("agent", route_after_model)  # to "tools" or the end
builder.add_edge("tools", "join")
builder.add_edge("join", "agent")

Because it is the only place that sees both results, the node owns everything that needs both: how many items each source gets, what happens when one source comes up short, the order, the numbering and the cards themselves. Only the marketplace variant of the graph has the node; tenants without the marketplace run the graph as before.

The budget: two plus three, per reply

Each reply shows at most five cards: two slots for the catalog and three for the marketplace. A source that cannot fill its share passes the unused slots to the other, so a search where one source finds nothing still returns a full list. Marketplace items come first; that was a product decision. Showing them first could steer spending away from the suppliers a company prefers in its own catalog, and the two reserved catalog slots are the protection against that.

The important word is reply, not search. One reply can search more than once: the model may search, read the results and search again. If every round got its own five cards, the total would creep up with every question. So each time the node runs, it recomputes the whole reply from scratch: it pools every search this reply has made, applies one budget across all of them and renumbers from one. A second search re-decides the same five slots rather than adding five more.

Recomputing from scratch keeps the state small. The node carries only two things between rounds: the ids of the tool calls this reply has budgeted, cleared at the start of every request, and, for each call, the rank each item had when that call first returned it. That second one is subtle. Two searches often overlap; a catalog’s “winter coats” are also its “jackets”. A shared item is kept under only one of the calls, which moves the other call’s items up its trimmed list. Interleaving on position would then change which query wins a slot from one round to the next. Interleaving on the rank each item was first seen at keeps the outcome stable.

One more presentation rule: numbers stay together per query, 1 and 2 for the first search, then 3 and 4, never 1 and 3 then 2 and 4. The client renders the model’s list as markdown, and markdown numbers a list itself, so any gaps in the model’s numbering would disappear on screen.

Show the model what the buyer sees

Once the node has chosen, it rewrites each search result in the conversation so it contains only the kept items, each with the position the buyer sees. LangGraph makes the rewrite simple. The messages reducer, add_messages, merges by id: a message with an id that is already in the state replaces the old one instead of being appended. It also gives every message an id as it is added, so by the time the join node runs, every tool result has one.

Replacing a tool result by id 
trimmed = ToolMessage(
    content=json.dumps(kept_envelope, ensure_ascii=False),
    tool_call_id=original.tool_call_id,
    name=original.name,
    id=original.id,  # same id: the reducer replaces the message in place
)
return {"messages": [trimmed]}

Trimming created a new problem: honesty. A call trimmed down to nothing looks exactly like a search that found nothing, and the model will tell the buyer the catalog has no hats when it has several. So each rewritten result also says how many items the call matched in total, and how many of its matches are already on screen under another query. The total never goes backwards between rounds. A later round reads the already-trimmed result, so recounting would shrink the number each time until it read as an empty catalog.

Send the cards from the node, not from the tools

Before the node existed, cards were built by a small function per tool when that tool finished. That is too early: it runs inside the tool node, in whatever order the tools complete, before anything has been budgeted. So the node now sends the cards itself, as a custom event, and the stream handler replaces the card list it shows instead of appending to it.

Sending the cards from the node 
from langchain_core.callbacks.manager import adispatch_custom_event
from langchain_core.runnables import RunnableConfig

# No "from __future__ import annotations" in this module: see below.
async def join_search_results(
    state: State, config: RunnableConfig | None = None
) -> dict:
    ...
    await adispatch_custom_event("search_cards", {"cards": cards}, config=config)

The card payloads travel on the event, not in graph state, so they are not written to the checkpoint.

Two details here cost me time.

First, LangGraph passes config to a node only when the parameter is annotated as RunnableConfig, alone or optional. With from __future__ import annotations at the top of the module, annotations become strings, the check fails, and LangGraph skips the injection with nothing louder than a warning. The node runs, config is None, and the event goes nowhere.

Second, the rewrite of the model’s view and the sending of the cards are one act. If the event could not be delivered, the screen still shows the previous round’s cards, and narrowing the model’s view now would strand items the buyer is looking at. So the node only rewrites the tool results when the cards went out. If no card has reached the buyer at all, it leaves the model free to list the items in text, so the reply is never empty.

What it cost

  • More steps. The node adds steps to every tool cycle, so the marketplace variant needs a higher step limit than the base graph.
  • Over-fetching. The catalog is asked for more candidates than its two slots, so there is material to fill the marketplace’s unused slots.
  • A new path in the stream handler. Its card list used to only grow; it needed a replace path. It must also flush held-back cards on every exit, or the saved conversation records cards the buyer never saw. The transcript rebuild needed its own card functions for this variant, too.
  • Code. A lot of careful code for what sounds like “take two and three”.

It was worth it. The model’s list and the cards on the screen are now built from the same items, so “add the last one” points at the same product for the buyer and for the model.

What I would keep

  • When parallel tools feed one screen, give their results a single meeting point in the graph, and let that node own every decision that needs more than one result.
  • Make the model’s view match the screen by replacing tool messages by id, rather than asking the prompt to keep them in line.
  • Budget per reply and recompute from scratch each round; carry only the state the recomputation cannot rebuild.
