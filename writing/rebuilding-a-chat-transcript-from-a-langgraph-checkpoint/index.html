Rebuilding a chat transcript from a LangGraph checkpoint

How I rebuilt a reopened chat from the messages the checkpointer already holds, without storing a second copy and without replaying a purchase.

27 Oct 2026

Smart Chat is the purchasing assistant in Vroozi’s procure-to-pay platform. A buyer asks for items, sees product cards as the searches finish, and asks for items to go into the cart or a purchase request. Buyers close the chat panel, reload the page and come back later. When they do, the conversation should be there as they left it: their messages, the replies, and the cards.

I built the endpoint that gives it back. This article is about the one decision that shaped it, and the three rules that followed from it.

Derive the transcript, don’t store it

The agent is a LangGraph graph with a checkpointer. Every message of a conversation is already saved under its thread, and our thread id is the chat session id. The agent resumes from that checkpoint on every request, so it is the source of truth for what happened.

The obvious alternative was a transcript table: write each turn as it streams, read it back on reopen. That is a second write on every turn, and two writes drift. A turn that fails halfway can land in one store and not the other, and from then on the chat the buyer reopens is not the chat the agent remembers.

So the endpoint reads the checkpointed state for the session and rebuilds the transcript from it. Nothing new is persisted. The cost is that the transcript is exactly as durable as the conversation itself, which in our case means as durable as the checkpointer. That was the right trade: a chat the agent can no longer continue is not one the buyer needs to see either.

Cards are a function of tool results

The awkward part was the product cards. They were never stored anywhere. While a reply streams, the handler takes each search tool’s result as the tool finishes and turns it into cards with a small formatting function per tool.

The checkpoint holds those same tool results. So the rebuild runs the same functions over the same messages: same code, same input, same cards. I did not write a second card builder for the transcript. Two builders would have drifted the first time someone changed one of them, and the reopened chat would have shown cards that never appeared live.

The same goes for duplicates. The stream de-duplicates cards within a reply, so the rebuild uses the same de-duplication function, not a look-alike.

One assistant turn per request

The checkpoint is a flat list: the buyer’s message, then model messages with tool calls, tool results, more model messages. The chat window shows one assistant turn per request the browser made. So the rebuild has to find where each request began.

A request starts with a message the buyer typed. It can also start without one. When the graph pauses before a cart or purchase-request action, the browser runs the action and posts the result back, and that result resumes the graph. In the checkpoint, it is a tool result for one of the client-action tools. Those two kinds of message are the only request boundaries; search results stay inside the request that asked for them.

A simplified sketch, not the production code:

Splitting the checkpoint into requests 
def requests_in(messages, client_action_tools):
    """Yield the checkpointed messages one request at a time."""
    request = []
    for message in messages:
        resumed = (
            isinstance(message, ToolMessage)
            and message.name in client_action_tools
        )
        if request and (isinstance(message, HumanMessage) or resumed):
            yield request
            request = []
        request.append(message)
    if request:
        yield request

Within each request, the assistant’s text is the model messages’ text joined with no separator, because that is how the stream accumulated it. The cards are whatever the search results in that request produce. A request with neither text nor cards produces no assistant turn.

Rule 1: never replay an action

In the live stream, a client action reaches the browser as an instruction: add this item to the cart, create this purchase request. If the rebuild produced those instructions again, reopening a chat could add an item twice or raise a second purchase request.

So the rebuild only runs the search card functions. The functions that turn a client action into an instruction are simply not in the map it uses. A restored conversation contains cards and text, never an action. I like that this holds by construction: there is no flag to forget, because the code path that could emit an action is not reachable from the rebuild.

Rule 2: a rebuild must not fail where the live turn did not

The live stream runs each card function inside its own error handling, so an odd tool result degrades quietly while the reply carries on. The rebuild has to be at least as forgiving, or one strange message makes the whole session impossible to reopen.

Two guards cover it. A tool call that failed live is checkpointed as an error message, and it produced no card at the time, so it contributes nothing now. Any other content a card function cannot parse is skipped with a warning instead of raising.

Being forgiving about content is different from hiding bugs. If reading the state itself fails, the endpoint returns a server error. Only two cases return “not found”: the session does not exist, or it is not yours.

Rule 3: rebuild for the right person, with their data

Two details matter for a purchasing tool.

Ownership is deny-by-default. When a conversation starts, its owner, both the tenant and the user, is recorded in the graph state. The endpoint compares both against the caller. A mismatch gets the same “not found” as a missing session, so the endpoint never confirms that someone else’s session exists.

Masked values need care too. Before text reaches the model, sensitive values are replaced with placeholders, and the checkpoint stores the masked version. The buyer sees the real values again because a mapping kept per session restores them. The read path could have reused the anonymizer object the stream uses, but that object is shared by the whole process and its mapping is mutable state. A read endpoint that loads a session’s mapping into shared state invites one request to see another session’s values. So the rebuild loads this session’s mapping and applies it with a pure function to a request-local copy. The shared object is never touched.

One trap: the graph has variants

Tenants who also buy from an external marketplace, such as Amazon Business, run a second variant of the graph. Its cards are built differently, by a join node that budgets cards across both sources (the subject of the next article). The rebuild has to use the card functions of the variant that served the session.

Get that wrong and nothing fails. The tool results simply do not match any function in the map, and the buyer reopens a chat with every card missing. Failures that raise no error need their own tests, one per variant.

What I would keep

  • If your UI shows something derived from tool results, keep that derivation a pure function of the checkpointed message, and reuse the exact same function on the read path.
  • Decide which outputs are safe to replay before you write the rebuild, and make the unsafe ones unreachable rather than switched off.
  • Treat a read path over shared, mutable state as a concurrency problem, even when it looks like a simple lookup.
