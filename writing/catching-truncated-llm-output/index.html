Catching truncated LLM output, even when the JSON still parses

A model that stops early does not always break your parser. Three checks that catch cut-off extractions, including the ones that come back as valid JSON.

27 Oct 2026

At Vroozi I designed and implemented the pipeline that turns invoices and purchase-request documents into structured data with Gemini on Vertex AI. Each document type has a Pydantic schema. The schema goes into the prompt, the model answers in text, and a recovery parser pulls the JSON out of that text before Pydantic validates it.

Language models stop early. Sometimes it is the output limit, sometimes the model simply decides it is done. Most advice about this is about the loud case, where the JSON is cut off mid-string and the parser throws. That case is the easy one. The case that hurt was the quiet one: the model closes its arrays and braces neatly, the JSON is valid, Pydantic is happy, and half the invoice is missing.

This article covers how we catch both.

The loud case: let the parse fail, then retry differently

The recovery parser tries three places in order: a fenced code block, then the text after a fence, then the text from the first brace. If none of them yields JSON, or Pydantic rejects what it found, the extraction is retried a fixed number of times, and each attempt uses different sampling settings. Retrying with identical settings tends to fail the same way twice.

If your provider reports why generation stopped, check that first. It is the cheapest signal you have, and a stop at the token limit tells you about the problem before you parse anything. But a stop reason cannot tell you that the content is incomplete, and incomplete content was our real problem.

There is a mirror image of this failure worth knowing about, because it taught me that “it parses” proves very little. A newer Gemini model started repeating the schema before its answer. The parser found the schema first, took it as the result, and it validated as an empty extraction with no error at all. I changed the parser to reject anything it recognizes as a schema and recover the real answer behind it, then proved the fix by replaying every affected document; each one re-parsed in full. Whether a model echoes its schema is now one of the checks when we try a newer model.

The quiet case, part one: the document has its own checksum

An invoice prints a subtotal. The line items on the page add up to it. That makes the document its own checksum: if the extracted line items add up to noticeably less than the extracted subtotal, lines are missing, whatever the JSON looks like.

So validation runs after parsing and compares the two. A shortfall beyond a small money tolerance is flagged as truncation, and it is blocking: the extraction is not passed on as complete. The opposite case, line items adding up to more than the subtotal, is blocking too, because it usually means the model invented or duplicated a line.

A simplified sketch of the idea:

Line items against the printed subtotal 
def check_line_items(invoice, tolerance):
    if invoice.subtotal is None or not invoice.line_items:
        return []
    total = sum(line.amount for line in invoice.line_items)
    if total < invoice.subtotal - tolerance:
        return [Violation("line_items_truncation", blocking=True)]
    if total > invoice.subtotal + tolerance:
        return [Violation("line_items_inflation", blocking=True)]
    return []

The real check is longer, because invoices are not that tidy. Discounts, credit lines and tax-inclusive totals all change what “adds up” means, and each needs its own rule. But the principle stayed the same: compare the extraction against a number the document printed, not against the model’s own idea of what it read.

The quiet case, part two: rows that collapse

Purchase-request documents taught us a second quiet failure. Estimates and quotations often group their rows under headings. Every so often the model returned one line per group instead of one per row, with the group’s printed subtotal as the unit price. Valid JSON, plausible values, often even the right total, and every individual item gone.

No arithmetic check catches that, because the totals still agree. So a detector compares the extraction with the document’s text instead. It fires only when three things hold together: the document prints many amounts, the extraction has very few rows, and those rows are named after the document’s group identifiers. When it fires, the extraction is retried.

The detector is deliberately narrow. A false alarm costs one extra model call on a healthy document, and some documents, such as fee summaries, naturally have few rows and many printed amounts. Whether a document should have many rows is a question of meaning, not of layout. So the detector targets the one collapse shape we had actually seen, and it is calibrated on our 41-document purchase-request regression set. Changing it means measuring it on that set again.

Repair: worth trying, worth measuring

Once validation can name what is wrong, it is tempting to hand the violations back to the model and ask it to fix its answer. We built that: an opt-in repair loop that re-prompts the model with the violations, bounded in both turns and time, and keeps the best result it has seen.

Then we measured it against runs without it. Repair cost 21 to 134 percent more tokens for an accuracy gain of 0.01 to 0.02. It is off by default and stays available as an opt-in. “The model can fix its own mistakes” is a claim to measure, not to assume.

What I would keep

  • Separate three outcomes and give each its own response. It did not parse: retry, with different settings. It parsed but it is wrong: validate against the document and block. It might be fixable: repair, but only where you have measured that it pays.
  • Look for redundancy in the source. Printed totals, counts and amounts are a free checksum for anything a model extracts.
  • Treat a narrow detector as a measured instrument. Write down what it was calibrated on, and measure again before you widen it.

If I started again, I would try the model’s structured-output mode instead of putting the schema in the prompt. That would remove the schema-echo failure rather than parse around it. It would not remove the quiet cases: a model can return perfectly structured output that is still missing half the document, which is why the checks above stay either way.
